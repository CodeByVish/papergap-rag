1) §4 标注规则（P2 点名要的 binary relevance / partial-evidence）
   - 版本：p5-annotation-v1（2026-10-28），P5 已定稿，等 P3/P6 批准。
   - 共享仓库 branch p5/generation-integration：
       docs/P5_ANNOTATION_RULE.md
     独立 P5 仓库：
       docs/WEEK5_QUALITY.md §4
   - 核心规则：
       * 每个 (question, passage) 给一个 0/1 标签；
       * 1 = passage 包含确定正确答案所必需的信息，不是“同主题/同实体/词面重合”；
       * 多部分问题：支持任一必需组件即 1，partial=1，并记录 component；
       * 不可回答问题：所有 passage 为 0，answerable=0；
       * 负证据算相关（答“否”也需要证据）；与 gold 矛盾且不提供正确事实的为 0；
       * 词面重合不算相关；
       * relevance 不等于 P5 的 provenance[].support（后者是“是否陈述了生成器的 claim”）；
       * 标注前盲测：不看 retrieval system、score、rank、gold answer、对方标签；
       * 协议：仲裁前算 raw agreement 和每对 Cohen's kappa，第三人仲裁，不能为了抬高 agreement 改标签。
   - 文件里还有边界案例表、标注字段、与 P5 validator 的关系。

   - 100 题 × 10 passage，固定 record order；

   - approval manifest：approved_by、pool_sha256、assignment ranges。
   P2/P5 独立标注同一批 334 条；P5 拿到这四件套后按 p5-annotation-v1 开始标注。

2) §4 是否批准

   - 如果 P3/P6 要改任何一条，请给版本号和变更点，P5 按新版本执行。

3) G5 runner 谁跑
   - P6 跑：需要 GPU（Qwen3-8B/vLLM），P5 提供 make_answer_fn、P6_HANDOFF/P6_RUNNER_HANDOFF 和 answer 记录格式；
   - P5 跑：P6 提供 runner 接口/导出格式，P5 在集群提交作业。
   请明确一种，避免两个 runner。

4) RAGAS judge 用 API 还是本地模型
   - API judge：P6 不需要 GPU，但要记录 judge model、prompt、参数、embedding model、成本；
   - 本地 judge：需要 GPU 配额。

5) held-out 最终生成谁跑
   - P6 跑或 P5 跑都可以；如果 P6 跑，需要 P5 的模型路径、vLLM venv 和 prompt/validator 配置。

三、GPU 需求（给 P6 排作业用）
======================================================================

不需要 GPU：
  - pool/manifest 构建、标注协调；
  - 读取 P5 的 answer JSONL、算 retrieval/QA 指标；
  - Streamlit UI；
  - RAGAS（如果 judge 走 API）。

需要 GPU：
  - P6 的 agent trace runner（G5，加载 Qwen3-8B/vLLM）；
  - held-out 最终生成（如果 P6 自己跑）；
  - RAGAS（如果 judge 用本地模型）；
  - BERTScore/embedding 类指标可选 GPU，CPU 也能跑。

集群约束（之前实测）：
  - 一个作业一整张 A40（45 GiB，无 MIG）；
  - 每次作业 6 小时上限；
  - GPU 只能通过 sbatch，登录节点不能跑模型；
  - P6 的 runner 可以共用 P5 已加载的 Qwen3-8B（GeneratorBackend.chat + make_answer_fn），避免重复加载。
